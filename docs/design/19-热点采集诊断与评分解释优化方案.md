# 热点采集诊断与评分解释优化方案

## 1. 背景

当前热点资讯模式已经具备 RSS、网页和 GitHub 来源管理、手动采集、来源隔离、标准化条目、相似事件聚合、中文化和每日 Top20 榜单。

现阶段的主要短板不是“能不能采到”，而是：

- 用户无法快速判断本次采集覆盖是否完整。
- 热度分只看来源数量和官方来源，缺少速度、新鲜度和生命周期。
- 写作价值分主要依赖关键词，缺少证据完整度、读者影响和历史反馈。
- 可信度没有区分独立来源、转载/重复来源和证据角色。
- 前端只有总分和一句理由，难以解释“为什么排在这里”。

## 2. 外部对标结论

### 2.1 Feedly AI

可借鉴点：

- 来源不是单个 URL，而是“主题规则 + 来源范围 + 包含/排除条件”。
- AI Models 与 AND/OR/NOT 组合可以减少关键词漏采和误采。
- 规则需要长期 refine，而不是每次临时输入关键词。

本阶段借鉴：

- 先保留现有来源 URL，但在评分和展示中补“采集覆盖率”和“来源组健康度”。
- 来源配置后续扩展 `includeTerms`、`excludeTerms`、`topicRules`，本阶段先不做复杂规则 UI。

### 2.2 BuzzSumo Trending

可借鉴点：

- Trending Score 关注传播速度，不等于累计分享数。
- 最近 24 小时内容与时间窗口是趋势判断的核心。
- 内容可保存到项目，后续用于研究和复盘。

本阶段借鉴：

- 新增 `velocityScore`，用最近窗口内新增独立来源和最后更新时间作为代理指标。
- 新增 `freshnessScore`，让刚出现且仍在更新的热点更靠前。
- 保留候选、确认、忽略状态，为后续“采纳率校准”打基础。

### 2.3 Exploding Topics

可借鉴点：

- 趋势判断应包含增长、速度、波动性、季节性、渠道分布和生命周期。
- 生命周期比单一热度分更容易帮助用户判断行动。

本阶段借鉴：

- 新增 `lifecycle`：`early`、`rising`、`peak`、`cooling`、`evergreen`。
- 暂不做预测模型，先用采集窗口和来源变化做确定性判断。

### 2.4 Google Trends

可借鉴点：

- 趋势数据应按时间窗口归一化。
- Rising 类指标强调相对前一时间段的增长。

本阶段借鉴：

- 在没有社交分享 API 的情况下，用“近 24 小时新增来源 / 近 72 小时来源总量”作为增长代理。
- 在页面文案中明确这是公开来源代理指标，不伪装成全网热度。

### 2.5 GitHub 开源方案

已参考 TrendRadar、ClawRadar、trend-pulse、hot-monitor 等方向。共同点是：

- 多来源采集后做去重和聚合。
- 评分拆成速度、时效、相关性或价值。
- 最终落到告警、日报、仪表盘或人工决策。

本阶段借鉴：

- 不只给一个总分，改为可解释评分明细。
- 采集运行和来源运行都要可诊断。

## 3. 产品目标

本阶段目标：

1. 让用户看懂一次采集是否可靠。
2. 让用户看懂一个热点为什么排在前面。
3. 让评分从“累计来源数”升级为“速度 + 新鲜度 + 证据 + 写作价值”。
4. 为后续人工反馈校准、选题简报和文章生成打好数据基础。

不做：

- 不引入复杂机器学习预测。
- 不绕过登录抓取社交平台。
- 不做自动定时采集。
- 不把代理热度描述为真实全网声量。

## 4. 采集诊断优化

### 4.1 批次级摘要

保留已有字段：

- `totalItems`
- `newItems`
- `dedupedItems`
- `status`
- `errorSummary`

新增展示计算：

- 启用来源数
- 成功来源数
- 失败来源数
- 覆盖率：成功来源数 / 请求来源数
- 本次新增率：新增条目 / 总条目

### 4.2 来源级明细

前端最近采集应展示每个来源：

- 来源名称
- 来源类型
- 状态
- 读取条数
- 新增条数
- 错误类型
- 错误摘要
- 开始和结束时间

这样用户能区分：

- “没有热点”是因为来源都正常但确实无新增。
- “没有热点”是因为主要来源失败。
- “部分成功”是否仍值得相信。

## 5. 评分模型

### 5.1 分数拆分

热点卡片保留三个主分：

- `writingScore`：排序主分，表示值得写的程度。
- `heatScore`：热度与扩散代理分。
- `confidenceScore`：证据可信度。

新增解释分：

- `velocityScore`：最近窗口新增速度。
- `freshnessScore`：时间新鲜度。
- `evidenceScore`：证据完整度。

新增结构化明细：

```json
{
  "sourceCount": 3,
  "officialCount": 1,
  "independentSourceCount": 2,
  "recentSourceCount": 2,
  "aiHits": 4,
  "depthHits": 3,
  "sourceGrowthRatio": 0.67,
  "freshnessHours": 8,
  "missingEvidence": [],
  "signals": ["官方来源", "24小时内新增", "多独立来源"]
}
```

### 5.2 热度分

热度分由以下因素组成：

- 来源覆盖：同一热点被多少来源采到。
- 独立来源：不同域名或不同渠道的来源数量。
- 速度：最近 24 小时新增来源占比。
- 官方来源：官方或一手来源加权。
- 新鲜度：最近一次出现距离现在的时间。

建议公式：

```text
heatScore =
  18
  + sourceCount * 10
  + independentSourceCount * 8
  + officialCount * 8
  + velocityScore * 0.25
  + freshnessScore * 0.15
```

### 5.3 速度分

```text
velocityScore =
  recentSourceCount / sourceCount * 60
  + recentSourceCount * 10
```

上限 100。没有社交分享数据时，明确它是“公开来源增量代理分”。

### 5.4 新鲜度分

按最后出现时间计算：

- 6 小时内：100
- 24 小时内：80
- 72 小时内：60
- 7 天内：35
- 更早：15

### 5.5 证据分

证据分关注来源质量：

- 官方/一手来源：强加分。
- 独立来源：不同站点或渠道加分。
- 社区或二手来源：加分较低。
- 只有单一社区来源：降权。

建议公式：

```text
evidenceScore =
  25
  + officialCount * 25
  + primaryCount * 18
  + independentSourceCount * 10
  + secondaryCount * 5
  - weakEvidencePenalty
```

`confidenceScore` 与 `evidenceScore` 保持一致或小幅考虑冲突证据。当前没有冲突证据表时，先等同于证据分。

### 5.6 写作价值分

写作价值分继续作为排序主分，但加入更多信号：

- AI 相关度。
- 深度信号。
- 证据完整度。
- 热度和速度。
- 官方或一手资料。
- 生命周期。

建议公式：

```text
writingScore =
  20
  + aiHits * 7
  + depthHits * 6
  + evidenceScore * 0.25
  + velocityScore * 0.15
  + freshnessScore * 0.10
  + lifecycleBonus
```

生命周期加分：

- `early`：+8，适合提前储备。
- `rising`：+12，优先推荐。
- `peak`：+6，适合快速解读。
- `cooling`：-8，除非证据很强。
- `evergreen`：+4，适合深度长文。

## 6. 生命周期判定

### 6.1 状态定义

| 生命周期 | 含义 | 适合动作 |
|---|---|---|
| early | 新出现，来源少但较新 | 观察或补证 |
| rising | 最近新增明显，且有多来源 | 优先确认选题 |
| peak | 来源多但增速一般 | 快速解读 |
| cooling | 旧热点，近期无新增 | 暂缓或忽略 |
| evergreen | 不新但价值高、证据完整 | 深度储备 |

### 6.2 判定规则

```text
if sourceCount <= 1 and freshnessScore >= 80:
  early
elif velocityScore >= 65 and sourceCount >= 2:
  rising
elif heatScore >= 70 and freshnessScore >= 60:
  peak
elif freshnessScore <= 35 and evidenceScore >= 70 and depthHits >= 2:
  evergreen
else:
  cooling
```

## 7. 前端展示

热点卡片新增：

- 生命周期标签。
- 速度分、新鲜度分、证据分。
- “为什么排在这里”明细区。
- 关键解释信号。

最近采集新增：

- 覆盖率。
- 成功 / 失败来源数。
- 每个来源的状态和错误。

页面说明应保持克制，只在指标旁用短标签说明“公开来源代理”。

## 8. 数据模型变更

### 8.1 `topic_clusters`

新增字段：

- `velocity_score` integer default 0
- `freshness_score` integer default 0
- `evidence_score` integer default 0
- `lifecycle` varchar default `early`
- `score_details_json` JSON default `{}`

### 8.2 API

`TopicView` 新增：

- `velocityScore`
- `freshnessScore`
- `evidenceScore`
- `lifecycle`
- `scoreDetails`

`SourceFetchRunView` 新增：

- `channelRuns`

其中 `channelRuns` 包含来源名称、类型、状态、条目数、新增数、错误码和错误摘要。

## 9. 验收标准

- 热点聚合后每条热点都有速度、新鲜度、证据、生命周期和结构化评分明细。
- `scoreReason` 不再只是关键词计数，而能说明来源、增速、证据和生命周期。
- 最近采集展示来源级成功/失败明细。
- 每日 Top20 排序仍由后端权威输出，前端只做同规则保护。
- 旧数据库通过迁移可升级，既有热点能用新公式重算。
- 热点专项测试、迁移测试、Ruff、mypy 和前端构建通过。
