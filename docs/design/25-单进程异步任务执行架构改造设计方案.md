# 单进程异步任务执行架构改造设计方案

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 文档状态 | 设计评审稿 |
| 目标 | 将当前多个 Worker 进程改造为一个 Worker 进程内的异步并发任务执行器 |
| 适用范围 | 课程生成、热点采集、热点资料研究、热点文章生成、图片生成、文章修复等后台任务 |
| 不在本次范围 | API 服务拆分、前端任务协议重写、数据库从 PostgreSQL 迁回其他数据库、公众号发布能力 |
| 推荐并发数 | 默认 2 个并发任务，通过配置调整 |
| 兼容原则 | 保持现有任务 API、任务状态、SSE 事件、工作流节点、重试和恢复行为不变 |

## 2. 背景与结论

当前项目的 `backend/app/workers/main.py` 已经使用 `asyncio`，模型调用和 HTTP 采集也大量使用异步接口，但 Worker 主循环仍然按以下方式执行：

```python
job = claim_next(...)
await execute_job(job.id)
```

因此，一个 Worker 进程一次只执行一个任务。当前能够同时处理两个任务，是因为启动了两个相同的 Worker 进程。

本方案将其改造为：

```text
一个 Worker 进程
    └── 一个 asyncio 事件循环
        ├── 任务调度器
        ├── 任务槽位 1 -> execute_job(job_a)
        ├── 任务槽位 2 -> execute_job(job_b)
        ├── 每个任务独立租约心跳
        └── 每个任务独立 SQLAlchemy Session
```

推荐采用“单进程 + asyncio Task + 有界并发”的兼容改造，而不是立即将所有 SQLAlchemy ORM 改为 `AsyncSession`。原因是当前工作流、任务服务、工作流节点和内容服务都基于同步 `Session`，一次性改造数据库访问层的影响面远大于 Worker 并发问题本身。第一阶段保留现有同步 ORM 接口，通过每个任务独立 Session 和短事务保证安全；后续只有在监控确认同步数据库操作成为事件循环瓶颈时，再单独推进异步数据库层改造。

## 3. 设计目标

### 3.1 必须达到

1. 一个 Worker 进程同时执行默认 2 个独立后台任务。
2. 一个任务失败、取消或超时，不影响同一进程中的其他任务。
3. 任务状态仍使用现有 `pending`、`running`、`succeeded`、`failed`、`cancelled` 等状态。
4. 保留现有任务创建、查询、SSE、事件续传、取消、失败重试和租约恢复接口。
5. 保留课程生成和热点文章生成现有工作流节点及记录方式。
6. 服务重启后，已过期任务仍能按现有规则恢复或失败收口。
7. API 服务和 Worker 可以独立重启，Worker 重启不导致任务永久停留在“执行中”。
8. 能明确观测当前运行任务数、等待任务数、并发上限、任务等待时间和执行耗时。

### 3.2 应当达到

1. 对不同任务类型设置独立资源上限，避免图片生成或外部采集占满全部槽位。
2. 保持先进先出调度，同时为后续优先级调度预留字段和接口。
3. 支持优雅停机：不再领取新任务，等待正在执行的任务到达安全检查点或超时收口。
4. 任务级取消使用现有数据库状态作为事实来源，内存中的 asyncio Task 只作为执行载体。
5. 日志中能够通过 `job_id`、`workflow_run_id`、`task_type` 和 `worker_instance_id` 关联一次执行。

### 3.3 明确不做

1. 不将任务状态只放入内存队列。数据库仍是唯一持久事实来源。
2. 不在多个协程之间共享 SQLAlchemy `Session`、工作流实例或可变任务状态。
3. 不通过提高并发数绕过模型供应商限流、图片接口额度或来源站点访问限制。
4. 不把课程生成中的图片子任务改为独立队列依赖任务。当前图片子任务由课程工作流内联执行，本方案先保持该语义，避免父任务等待子任务造成槽位死锁。
5. 不修改现有前端任务状态协议。前端只继续读取数据库任务状态和持久化事件。

## 4. 当前实现审计

### 4.1 当前组件关系

| 组件 | 当前行为 | 改造影响 |
|---|---|---|
| FastAPI API | 独立进程，创建/查询/取消任务 | 无需改公开接口 |
| `jobs` 表 | 保存任务状态、进度、租约、重试次数和结果 | 保留原字段；可追加诊断字段 |
| `job_events` 表 | 保存可重放进度事件 | 保留，事件仍在事务中写入 |
| `workflow_runs` | 保存工作流总体状态和节点关联 | 保留 |
| `JobService.claim_next` | 原子领取一条 `pending` 任务，PostgreSQL 使用 `SKIP LOCKED` | 扩展为批量补槽位或重复调用 |
| `execute_job` | 每次执行一个任务，当前内部创建 Session | 改为每个异步任务独立生命周期 |
| `_heartbeat` | 每个任务一个异步心跳协程 | 保留，纳入运行任务句柄 |
| `recover_expired` | 重启或轮询时收回过期租约 | 保留并限制重复执行 |
| 工作流 | 多数为异步模型调用 + 同步 ORM 操作 | 保持接口，禁止共享 Session |
| 图片子任务 | 课程工作流创建子 Job 后直接调用图片工作流执行 | 保持内联，不进入调度器等待队列 |

### 4.2 当前串行原因

当前 `run_worker()` 中，任务领取后会直接等待任务完成：

```python
while not stop_event.is_set():
    job = claim_next(...)
    if job is None:
        await asyncio.sleep(...)
        continue
    await execute_job(job.id)
```

虽然 `execute_job()` 内部会 `await` 文本模型、图片模型和 HTTP 请求，但主循环在这个 `await` 返回前不会再次领取任务。因此，异步函数并不等于任务级并发；必须由调度器创建多个独立的 AnyIO task。

### 4.3 成熟组件与第三方依赖选型

Python 生态中有与 Java `jar` 依赖相同用途的包，通常通过 PyPI 发布，并在本项目的 `pyproject.toml` 与 `uv.lock` 中锁定版本。本改造不应手写通用并发框架，而应在不替换现有业务任务体系的前提下组合成熟组件。

#### 4.3.1 候选方案对比

| 方案 | 原生异步 | 持久介质 | 单进程并发 | 对现有系统影响 | 结论 |
|---|---|---|---|---|---|
| Python 3.12 `asyncio` | 是 | 无，自行接 PostgreSQL | 是 | 最小 | 作为事件循环与 Task 基础设施 |
| `AnyIO` | 是 | 无，自行接 PostgreSQL | 是 | 小 | 推荐，负责结构化并发、取消、超时和线程隔离 |
| `aiometer` | 是 | 无 | 是 | 小 | 推荐用于模型、图片、来源请求的并发数和速率限制 |
| `Procrastinate` | 是 | PostgreSQL | 是 | 中到大 | 最匹配现有数据库的完整任务队列，作为后续替换选项 |
| `ARQ` | 是 | Redis | 是 | 大 | 需要新增 Redis，并迁移现有任务状态，不选 |
| `Taskiq` | 是 | 依赖 Broker 插件 | 是 | 大 | 功能完整，但会引入新的 Broker 和任务协议，不选 |
| `Celery` | 不以 asyncio 原生协程为核心 | Redis/RabbitMQ 等 | 通常使用进程/线程池 | 很大 | 适合分布式任务，不符合本次单进程原生异步目标 |
| `Dramatiq` | 主要是进程/线程 Worker 模型 | Redis/RabbitMQ | 可配置 | 很大 | 会替换现有 Worker 和重试体系，不选 |
| `APScheduler` | 支持异步调度 | 可配置 Job Store | 是 | 中 | 面向定时调度，不是本项目的持久消费队列，不选 |

当前 PyPI 信息显示：`Procrastinate` 定位为基于 PostgreSQL 的分布式任务处理库；`ARQ` 明确依赖 Redis；`Taskiq` 提供完整异步任务队列；`aiometer` 专门提供 asyncio/Trio 并发调度能力；`AnyIO` 是 asyncio/Trio 之上的高层并发框架。选型应依据系统边界，而不是仅比较功能数量。

#### 4.3.2 最终推荐组件组合

**`AnyIO 4.x`：协程生命周期和全局并发计数**

`AnyIO` 相当于并发控制基础库，负责：

- Task Group：统一创建、等待和关闭多个任务。
- `CapacityLimiter`：首期只实现全局任务槽位；文本模型、图片和采集的调用点限流放到第二阶段。
- Cancel Scope：实现单任务取消和 Worker 优雅停机，不误取消兄弟任务。
- `fail_after()` / `move_on_after()`：实现任务总超时和停机宽限期。
- `to_thread.run_sync()`：隔离 Pillow、大文件处理或暂时无法异步化的同步阻塞代码。

虽然 FastAPI 已间接依赖 AnyIO，但项目如果直接导入它，必须把 `anyio>=4,<5` 写入 `pyproject.toml`，不能依赖传递依赖偶然存在。

**`aiometer 1.x`：第二阶段的上游调用并发和速率限制**

`aiometer` 负责第二阶段批量异步调用的两类限制：

- `max_at_once`：同一时间最多有多少个请求在执行。
- `max_per_second`：每秒最多发起多少个请求。

它适用于多来源热点采集、资料池多个搜索来源、批量模型调用和图片供应商接口。顶层任务并发仍由 `AnyIO CapacityLimiter` 管理；`aiometer` 只管理一个任务内部或同类上游请求，不能代替持久任务队列。首期不引入它，避免调度、Session 和上游限流同时变更。

**SQLAlchemy + psycopg：继续作为持久任务与原子领取基础**

继续复用现有成熟依赖：SQLAlchemy 负责 ORM、事务和连接池，psycopg 负责 PostgreSQL 驱动，`SELECT ... FOR UPDATE SKIP LOCKED` 负责原子领取，`jobs`、`job_events` 和 `workflow_runs` 继续作为唯一业务状态来源。这部分已经在项目中运行，无需引入 Redis 或 RabbitMQ。

**`Procrastinate`：完整队列替换的候选，不在首期混用**

如果以后需要多机分布式 Worker、内建队列、定时任务和统一重试，可以单独立项迁移到 `Procrastinate`。它使用 PostgreSQL，不需要新增 Redis，是完整队列替换时最符合当前基础设施的候选。

本轮不直接接入的原因不是它不成熟，而是当前项目已经有与前端、SSE、工作流节点、课程重试和图片子任务紧密绑定的 `jobs` 体系。直接混用会产生：

1. 现有 `jobs` 表和 Procrastinate 内部任务表两套状态。
2. API 创建任务和队列入库之间的双写一致性问题。
3. 两套重试次数、取消状态和失败原因。
4. 现有 `job_events` 与队列执行事件的同步问题。

除非整体迁移任务存储，否则不应把它只套在现有 Worker 外层。若未来迁移，应通过 Outbox、幂等键和状态投影进行完整设计。

#### 4.3.3 依赖锁定建议

阶段 A 新增直接依赖：

```toml
dependencies = [
    "anyio>=4.14,<5",
]
```

实施时使用 `uv add` 生成并提交 `uv.lock`，禁止运行时动态安装。正式最小版本应以兼容测试结果为准，不仅依据最新版本。

阶段 B 再按真实采集和模型调用的限流需求增加：

```toml
"aiometer>=1.0,<2",
```

不需要新增以下组件：

- 不需要 Redis：现有 PostgreSQL 已承担持久队列和租约。
- 不需要 RabbitMQ：当前是单机单 Worker 进程，没有独立 Broker 的收益。
- 不需要线程池作为主执行器：文本、图片和采集主要是异步 I/O；线程只用于少量同步阻塞适配。
- 不需要 Celery Beat 或 APScheduler：本次解决的是已入队任务并发，不是定时任务编排。
- 不需要自行实现计数器：并发槽位由 `CapacityLimiter` 管理，速率由 `aiometer` 管理。

#### 4.3.4 组件边界示例

```python
import anyio

global_limiter = anyio.CapacityLimiter(2)

async def execute_claimed_job(job_id: str) -> None:
    async with global_limiter:
        with anyio.fail_after(timeout_for_job(job_id)):
            await run_job_with_own_session(job_id)
```

阶段 B 的调用点限流示例：

```python
import aiometer

async def collect_sources(calls):
    return await aiometer.run_all(
        calls,
        max_at_once=settings.worker_fetch_concurrency,
        max_per_second=settings.worker_fetch_rate,
    )
```

示例只表达组件职责。生产实现仍需要数据库领取、任务注册表、租约心跳、异常终态和优雅停机，不能仅把工作流放进并发库。

### 4.4 当前必须保留的行为

1. 领取任务前将状态原子修改为 `running`。
2. 任务运行期间定期续租。
3. 任务进度和工作流节点事件持久化后供 SSE 读取。
4. `AppError` 显示安全错误信息，未知异常显示统一任务失败信息并写详细服务端日志。
5. 热点采集失败时保留已采集内容并收口采集运行状态。
6. 课程任务重试时，已生成的公众号原稿和图片可以按现有规则复用。
7. 任务取消先进入 `cancellation_requested`，由工作流在安全检查点完成终态取消。

## 5. 目标架构

### 5.1 进程模型

```text
FastAPI API 进程
    └── 只处理 HTTP、SSE 和数据库短事务

Async Worker 进程
    ├── Scheduler：领取任务、填充并发槽位、回收完成任务
    ├── Task Registry：记录当前 AnyIO task 与 job_id 的映射
    ├── Global CapacityLimiter：首期限制同时执行的顶层任务数
    ├── Call-site Limiters：第二阶段限制图片、文本、采集等外部资源
    ├── Lease Manager：每个任务续租和退出清理
    └── Job Executor：运行现有工作流并提交终态

PostgreSQL
    ├── jobs
    ├── job_events
    ├── workflow_runs
    ├── workflow_nodes
    └── model_calls / 业务结果表
```

### 5.2 调度循环

调度器不再等待一个任务完成，而是持续把空闲槽位填满：

```python
async def run_worker() -> None:
    await recover_on_startup()
    limiter = anyio.CapacityLimiter(settings.worker_concurrency)

    async with anyio.create_task_group() as task_group:
        while not shutdown_requested:
            await reap_finished()
            await recover_expired_jobs()
            while limiter.available_tokens > 0:
                job = claim_one_job()
                if job is None:
                    break
                # start() waits until the child has acquired its slot and registered job_id.
                await task_group.start(execute_claimed_job, job.id, limiter)
            await wait_for_next_wakeup()

        with anyio.move_on_after(settings.worker_shutdown_grace_seconds):
            await wait_for_running_jobs()
```

实际实现中，`claim_one_job()` 的数据库写操作仍使用同步 `SessionLocal`，但必须在调用后立即关闭 Session；不能把领取阶段的 Session 传给任务协程。`TaskGroup` 不能因为一个任务失败而取消所有兄弟任务，因此任务入口必须捕获并收口业务异常，调度器只负责回收执行结果。

使用 `TaskGroup.start()` 而不是连续 `start_soon()`，是为了让子任务在占用全局槽位并写入注册表后再返回调度循环，避免事件循环尚未调度子任务时一次领取超过并发上限的任务。

`execute_claimed_job()` 需要接收 AnyIO 的 `task_status` 参数，并在完成“获取全局槽位、注册 `job_id`、启动任务级心跳”后调用 `task_status.started()`；如果任务在注册前失败，调度器必须把刚领取的任务恢复为 `pending` 或安全失败。

### 5.3 任务句柄

每个运行任务维护以下内存信息：

```python
class RunningJob:
    job_id: str
    cancel_scope: anyio.CancelScope
    done_event: anyio.Event
    claimed_at: datetime
    task_type: str
```

内存信息用于调度和清理，数据库中的 `jobs.status`、`lease_expires_at` 和 `job_events` 仍是对外状态来源。进程崩溃后不能依赖内存信息恢复任务，必须依靠租约恢复。

## 6. Session 与事务设计

### 6.1 核心规则

这是本次改造最重要的安全边界：

1. 每个 AnyIO 任务创建一个独立的 `SessionLocal()`。
2. API 请求使用自己的 Session，与 Worker 协程完全隔离。
3. 不允许把 Scheduler 的 Session、Job ORM 对象或 Workflow ORM 对象传入执行协程。
4. 任务在 `execute_claimed_job(job_id)` 开始时重新查询任务，不能依赖领取时已脱离 Session 的 ORM 对象。
5. 进度、节点状态、结果提交和错误收口使用短事务并及时 `commit()`；禁止事务或未提交 ORM 状态跨越 LLM、图片、HTTP 等长时间 `await`。
6. 捕获异常后先 `rollback()`，再用新的查询结果执行失败收口。
7. 任务结束时关闭 Session，防止连接长期占用。

### 6.2 同步 SQLAlchemy 的兼容处理

第一阶段不要求把全项目改为 `AsyncSession`，但不能因此保留“一个 Session 包住整个工作流”的现状。第一阶段至少要把任务执行 Session、进度 Session 和终态 Session 分开，并在每个工作流节点的 `await` 前提交并释放事务；第二阶段再把所有复杂节点改成明确的“读取快照 -> 异步调用 -> 短事务写回”结构。为了避免意外阻塞事件循环：

- 领取、恢复、状态更新等短数据库操作可直接执行，但必须有明确事务边界。
- 工作流进入模型或 HTTP 调用前，必须完成当前节点的数据库提交或回滚并关闭 Session；调用返回后重新打开 Session 写入结果。
- `progress_reporter` 不得闭包捕获长生命周期 Session，应接收 `SessionFactory` 或调用短事务的 Job Event Writer。
- 终态提交必须重新查询任务，不能复用跨 `await` 的 ORM 对象。
- 需要大量查询、批量导入或图片文件读写的辅助操作，应通过 `anyio.to_thread.run_sync()` 或独立同步适配器执行。
- 不得在 `to_thread()` 中使用属于另一个协程的 Session。
- 不得在工作流中调用 `time.sleep()`、同步 HTTP 客户端或无限期阻塞的文件操作。
- 后续如监控发现事件循环延迟超过阈值，再将公共 Repository 层迁移到 SQLAlchemy AsyncSession；这应作为独立项目，不与本次 Worker 改造混合。

### 6.3 连接池容量

单进程并发并不意味着只需要一个数据库连接。建议按以下公式配置 PostgreSQL 连接池：

```text
pool_size >= API 并发保留连接 + Worker 并发数 + 事件/SSE 查询余量
```

以默认 Worker 并发数 2 为例，现有 `pool_size=10`、`max_overflow=20` 足够第一阶段使用。每个任务不能持有事务跨越模型调用，否则会长期占用连接并增加锁等待。

## 7. 租约、心跳与重复执行防护

### 7.1 领取流程

1. 调度器查询最早的 `pending` 任务。
2. PostgreSQL 使用 `FOR UPDATE SKIP LOCKED`，兼容迁移期间仍存在的旧 Worker。
3. 原子更新为 `running`，写入 `started_at` 和 `lease_expires_at`。
4. 提交领取事务并关闭领取 Session。
5. 只有领取提交成功后才创建 AnyIO task。

如果创建执行 Task 失败，必须立即将该任务重新置为 `pending` 或记录失败，不得让任务只剩一个无人续租的 `running` 状态。

### 7.2 心跳流程

每个执行协程独立创建心跳任务，心跳生命周期绑定该任务，不绑定全局 `stop_event`：

```text
execute_job(job_id) ────────┐
                            ├── heartbeat(job_id)
                            └── finally: cancel heartbeat
```

心跳只更新该 `job_id` 的租约，不更新进度、不读取工作流状态、不共享执行 Session。心跳更新失败时写日志并在下一周期重试；连续失败达到阈值时，执行任务应停止提交新的昂贵上游请求，并进入失败或可恢复状态。

收到 Worker 停机信号后，只停止调度器领取新任务；每个正在 drain 的任务继续保持自己的心跳，直到任务完成、任务级 Cancel Scope 结束或停机宽限期到达。不能让心跳直接依赖全局 `stop_event`，否则停机宽限期内租约可能过期并被恢复逻辑重复领取。

### 7.3 任务完成与旧租约

`succeed()`、`fail()`、`complete_cancellation()` 和工作流终态写回必须带状态条件，并返回是否实际更新成功。例如：

```sql
UPDATE jobs
SET status = 'succeeded', lease_expires_at = NULL
WHERE id = :job_id AND status = 'running'
```

如果 `rowcount=0`，当前执行协程不能再覆盖任务，也不能把失败误报成成功；只记录 `job_terminal_update_skipped` 日志并释放资源。对于 `cancellation_requested`，统一进入 `complete_cancellation()`，不能由 `succeed()` 抢先覆盖。工作流状态和通知写入也必须位于同一短事务，且以任务状态更新结果为准。这样可以避免网络抖动或租约恢复后旧协程写回结果。

课程图片内联子任务是现有兼容例外：它当前创建后保持 `pending`，随后由父课程任务直接执行。落地条件终态更新前，必须新增 `start_inline_child()`，以条件更新将该子任务从 `pending` 改为 `running` 并写入开始事件；图片完成后才能统一调用受状态保护的 `succeed()` 或 `fail()`。不能为兼容内联任务而放宽顶层任务的终态条件。

### 7.4 恢复策略

启动时和调度循环中继续调用 `recover_expired()`，但建议增加以下保护：

- 同一轮调度只执行一次恢复扫描。
- 只恢复 `running` 且 `lease_expires_at < now` 的任务。
- 恢复前再次确认任务不在当前进程 `running` 注册表中；实现必须把这一条写成不可绕过的条件，而不是仅记录日志。
- 若当前进程仍有该任务，即使心跳短暂失败，也不由同一个进程重新领取；由该任务级超时/看门狗负责停止原 Task，再进入失败或重新排队。这样避免同一进程内双执行。
- 达到 `max_retries` 后保持现有失败收口，不自动无限重试。

## 8. 并发控制策略

### 8.1 全局并发槽位

新增配置：

| 配置 | 默认值 | 说明 |
|---|---:|---|
| `CHENGWENFANG_WORKER_CONCURRENCY` | `2` | 单个 Worker 进程最多同时执行的顶层任务数 |
| `CHENGWENFANG_WORKER_POLL_SECONDS` | `1.0` | 无任务时的轮询间隔，保留现有配置 |
| `CHENGWENFANG_WORKER_SHUTDOWN_GRACE_SECONDS` | `60` | 优雅停机等待时间 |
| `CHENGWENFANG_WORKER_MAX_CLAIMS_PER_CYCLE` | `2` | 一轮调度最多领取的任务数 |
| `CHENGWENFANG_WORKER_EXECUTION_MODE` | `single_async` | 执行模式；`legacy_serial` 表示单进程并发数为 1 |

`CHENGWENFANG_WORKER_CONCURRENCY=1` 时行为等价于当前单 Worker 串行执行，可作为故障排查和回滚开关。首期不在任务入口按 `job.type` 获取类型槽位，避免课程任务同时包含文本和图片阶段时占死资源；类型限流统一下沉到第二阶段的实际调用点。

### 8.2 类型级资源限制

第二阶段的调用点限流设计如下，首期不实现：

| 资源 | 建议默认值 | 保护对象 |
|---|---:|---|
| 文本模型调用 | 2 | 课程原稿、公众号文章、热点文章、改写和核验 |
| 图片模型调用 | 1 | 图片生成接口和本地图片处理 |
| 来源采集 | 2 | RSS、网页和 GitHub HTTP 请求 |
| 本地 CPU/文件处理 | 1 | 大文本解析、图片归一化和批量导入 |

文本、图片和采集调用点分别使用 `aiometer` 或 `AnyIO CapacityLimiter`，资源信号量必须在 `finally` 中释放，避免异常导致永久占用。任务入口只占全局槽位。

### 8.3 公平性

第一阶段继续按 `created_at, id` FIFO 领取任务，保证现有行为稳定。后续可以增加任务优先级，但必须同时定义：

- 热点采集是否优先于文章生成。
- 长任务是否允许被短任务插队。
- 同一课程或同一选题是否只能存在一个活跃任务。
- 是否需要每种任务的保留槽位，避免图片生成长期阻塞文本生成。

本次不修改任务排序规则，避免改变用户当前感知。

## 9. 任务执行生命周期

### 9.1 标准流程

```text
pending
  ↓ 原子领取
running / starting
  ↓ 创建执行 Task
running / 节点进度
  ├── succeeded / completed
  ├── failed / error
  ├── cancellation_requested
  │       ↓ 安全检查点
  │   cancelled
  └── Worker 崩溃或租约过期
          ↓ recover_expired
      pending / recovered 或 failed
```

### 9.2 执行协程职责

建议将当前 `execute_job()` 拆为以下职责，但不改变各工作流的公共接口：

1. `load_claimed_job(job_id)`：使用独立 Session 读取任务和工作流。
2. `acquire_global_slot()`：获取全局并发槽位；首期不按 `job.type` 占用类型槽位。
3. `run_job_workflow(job_id)`：调用现有工作流。
4. `finalize_success(job_id, output)`：独立短事务提交成功状态。
5. `finalize_app_error(job_id, error)`：回滚当前事务后安全失败收口。
6. `finalize_unexpected_error(job_id, error)`：记录内部日志并提交统一错误。
7. `release_resources()`：释放全局并发槽位并关闭 Session；阶段 B 再释放调用点资源限流器。

不能让异常从执行 task 直接冒泡到根 TaskGroup，导致兄弟任务被取消。任务入口必须捕获 `AppError`、超时和未知异常并完成数据库终态收口；调度器只回收已完成句柄并记录日志。

### 9.3 进度事件

当前工作流通过 `progress_reporter` 写 `jobs` 和 `job_events`。改造时保留该机制，但需注意：

- 每个报告器绑定固定 `job_id`，不能引用调度器当前任务变量。
- 同一任务的进度可能因并发的心跳或子节点回调交错到达，必须按该任务自己的事件顺序写入。
- 不允许用全局变量保存“当前 job”。
- SSE 继续按 `job_events.id` 续传，前端无需感知进程内并发。

## 10. 父子任务与工作流兼容

### 10.1 现有课程图片子任务

课程生成工作流会创建图片 Job 记录，但随后在同一课程工作流中直接调用 `ImageGenerationWorkflow.run()`，完成后再更新图片子 Job。这是一种“持久化子任务记录 + 内联执行”的模式。

本次改造继续保留：

- 图片子任务不进入顶层调度器队列。
- 父课程任务不会等待一个由自己占用槽位的子任务。
- 图片调用的资源限流在阶段 B 才接入；阶段 A 只受全局任务槽位控制。
- 图片子任务的成功、失败和素材记录仍按现有逻辑写入。

### 10.2 后续拆分子任务的约束

若未来要将图片子任务真正交给队列，必须先实现依赖调度模型，至少包括：

- `parent_job_id`、`depends_on_job_id` 或等价依赖字段。
- 父任务挂起时释放顶层槽位，而不是占着槽位等待子任务。
- 子任务完成后通过事件唤醒父任务恢复节点。
- 子任务失败时定义父任务失败、降级或继续策略。
- 同一任务链的幂等键和结果复用策略。

在这些条件完成前，不把当前内联子任务改为排队子任务。

## 11. 取消、超时与优雅停机

### 11.1 用户取消

现有 API 将 `running` 任务改为 `cancellation_requested`。执行协程在以下位置检查取消：

- 每次持久化进度前。
- 每个模型调用前。
- 批量来源采集的每个来源之间。
- 图片生成前和图片结果保存前。
- 工作流节点切换前。

检测到取消后，调用现有 `complete_cancellation()`。不能直接依赖底层 task cancel 作为用户取消，因为它可能中断数据库事务和文件保存；用户取消使用任务级 Cancel Scope 和安全检查点。

### 11.2 上游超时

每类上游请求保留当前客户端超时和重试策略，并在任务层增加总时限：

```python
with anyio.fail_after(timeout_for_job(job_id)):
    await run_job_workflow(job_id)
```

总时限到达后：

1. 停止继续发起新的上游请求。
2. 回滚未提交事务。
3. 写入可读错误码，例如 `JOB_TIMEOUT`。
4. 按任务重试预算决定重新排队还是失败。
5. 释放所有信号量和 Session。

### 11.3 Worker 优雅停机

收到 `SIGINT` 或 `SIGTERM` 后：

1. 设置 `shutdown_requested`，停止领取新任务。
2. 保留已有任务的心跳。
3. 等待运行任务完成或进入安全取消点。
4. 到达 `shutdown_grace_seconds` 后，对剩余执行 Task 发送取消信号。
5. 任务若未能写终态，关闭 Session，等待租约过期后由下次启动恢复。
6. 记录 `worker_stopped` 和未完成任务列表。

不能在停机时直接把执行中的任务批量标记为失败，否则会丢失本可以恢复的工作流状态。

## 12. 错误隔离与恢复

### 12.1 单任务隔离

每个任务使用独立 AnyIO task，调度器通过 `TaskGroup` 和任务注册表回收异常。禁止使用不检查异常的裸 `asyncio.gather()` 或让业务异常冒泡到根 TaskGroup。

推荐：

```python
async with anyio.create_task_group() as task_group:
    task_group.start_soon(execute_claimed_job, job_id, limiter)
    await wait_for_next_wakeup()
```

一个任务抛出异常只触发该任务的失败收口，不取消其他任务；执行入口必须捕获 `AppError`、超时和未知异常，并在退出前提交任务终态。

### 12.2 任务级重试

继续使用现有 `retry_count` 和 `max_retries`。重试必须满足：

- 旧执行协程已经退出或租约失效。
- 任务状态已经回到 `pending`。
- 原工作流记录和节点日志保留。
- 不重复覆盖已经成功提交的文章版本、图片资产和资料池结果。
- `retry_failed` 的现有“课程任务复用已完成原稿/图片”逻辑继续生效。

### 12.3 进程级故障

单进程模型的代价是 Worker 进程崩溃会同时影响所有正在运行的任务。通过以下措施降低风险：

- 每个任务独立租约和心跳。
- 任务状态全部持久化。
- 启动恢复扫描。
- 管理脚本或服务管理器自动重启 Worker。
- 关键异常写结构化日志。
- 生产环境保留 `CHENGWENFANG_WORKER_CONCURRENCY=1` 的降级选项。

如未来需要“一个任务崩溃不影响其他任务”的更强隔离，应重新引入多进程或外部队列，不通过线程/协程模拟进程隔离。

## 13. 数据库与迁移方案

### 13.1 第一阶段可不迁移表结构

现有 `jobs`、`job_events`、`workflow_runs` 和租约字段已经足够支撑单进程异步并发。首版改造可以只修改 Worker、配置、启动脚本和测试，不改变业务表结构，降低发布风险。

### 13.2 建议的增量诊断字段

诊断字段推迟到阶段 C。阶段 A 只使用结构化日志，确认字段确有查询和运维价值后，再新增向后兼容的 Alembic 迁移：

| 字段 | 类型 | 用途 |
|---|---|---|
| `worker_instance_id` | `VARCHAR(128) NULL` | 标记最后领取/执行该任务的 Worker 实例 |
| `heartbeat_at` | `TIMESTAMP WITH TIME ZONE NULL` | 记录最后一次成功续租时间 |
| `claimed_at` | `TIMESTAMP WITH TIME ZONE NULL` | 区分排队时间和实际领取时间 |

所有字段允许为空，旧数据和旧 Worker 均可继续工作。若暂时不增加字段，至少在结构化日志中输出同等信息。

### 13.3 领取查询

单进程模式仍保留 `SKIP LOCKED`，原因是：

- 发布切换期间可能存在短暂的旧 Worker。
- 运维人员可能手动启动临时 Worker。
- API 或恢复逻辑不会因为单进程假设而误领任务。

## 14. 配置与启动改造

### 14.1 后端配置

在 `Settings` 中增加：

```python
worker_concurrency: int = 2
worker_shutdown_grace_seconds: int = 60
worker_max_claims_per_cycle: int = 2
worker_execution_mode: str = "single_async"
worker_default_task_timeout_seconds: int = 1800
worker_course_task_timeout_seconds: int = 7200
worker_fetch_task_timeout_seconds: int = 900
```

所有数值都需要通过 Pydantic 范围校验：并发数至少为 1，超时和轮询间隔必须为正数。任务总超时按类型解析，课程完整生成使用较长时限，热点采集使用较短时限，未知任务回退到默认值；不能用统一 1800 秒误杀长课程任务。文本、图片和采集调用点并发配置在阶段 B 增加。

### 14.2 启动脚本兼容

当前 `scripts/dev.ps1` 的 `-WorkerCount` 参数不能直接删除，否则会破坏已有启动命令。建议：

1. 保留参数一版。
2. 无论 `-WorkerCount` 传入多少，都只启动一个 Worker 进程。
3. `-WorkerCount > 1` 将数值映射为 `CHENGWENFANG_WORKER_CONCURRENCY` 并输出弃用提示，不再保留隐式多进程分支。
4. 新增 `-WorkerConcurrency` 参数，优先级高于 `-WorkerCount`；二者同时传入时只采用 `-WorkerConcurrency`。
5. 文档和默认命令改为：

```powershell
scripts\dev.ps1 -Service all -WorkerConcurrency 2
```

正式切换后，脚本应保证 API、前端和 Worker 进程数量分别为 1、1、1。

## 16. 实施阶段

### 阶段 A：最小可靠并发改造

阶段 A 只解决“一个进程同时执行两个顶层任务”，同时补齐并发后必须具备的一致性保护，不引入类型级限流和数据库字段迁移。

1. 增加 `single_async` 与 `legacy_serial` 开关，默认先保持旧模式。
2. 使用 AnyIO `TaskGroup`、`CapacityLimiter` 和任务注册表实现全局并发 2。
3. 每个任务建立独立执行上下文、Session、任务级心跳和 Cancel Scope。
4. 调度器 Session、进度 Session 和终态 Session 使用短事务，禁止共享。
5. `succeed()`、`fail()`、`complete_cancellation()` 改为条件更新并返回布尔结果。
6. 课程图片内联子任务增加 `start_inline_child()`，统一进入受保护终态。
7. `recover_expired()` 接收当前进程活跃 `job_id` 集合并硬性排除。
8. Worker 停机后停止领取任务，但 drain 期间继续所有活跃任务心跳。
9. 任务总超时按任务类型配置；首期只记录事件循环延迟日志。
10. 启动脚本始终只创建一个 Worker 进程，旧 `WorkerCount` 映射为并发数并提示弃用。
11. 先以并发数 1 完成回归，再切换到并发数 2 做真实验收。

阶段 A 完成标准：现有 API、SSE、前端、任务状态、工作流节点和业务结果不变，两个独立 I/O 任务可重叠执行，且不存在重复领取和旧协程覆盖终态。

### 阶段 B：调用点限流与工作流短事务深化

阶段 B 在阶段 A 稳定后实施，不与调度器改造同批发布。

1. 审计所有模型、图片和 HTTP `await`，改为“读取快照 -> 结束事务 -> 异步调用 -> 新短事务写回”。
2. 将 `progress_reporter` 改为独立短事务事件写入器，不捕获工作流长生命周期 Session。
3. 在 `text_client`、`image_client` 和热点采集调用点引入类型级 `CapacityLimiter` 或 `aiometer`。
4. 图片生成、Pillow 处理和大文件操作按测量结果使用 `anyio.to_thread.run_sync()`。
5. 增加供应商级每秒速率限制和 429/超时指标。
6. 对连接池占用、事务时长和事件循环延迟进行专项验收。

阶段 B 完成标准：任何外部网络等待期间不持有未提交数据库事务；类型限流只作用于真实资源调用点，不在任务入口按 `job.type` 一刀切。

### 阶段 C：可选诊断字段与异步数据库层

只有监控数据证明有必要时才实施：

1. 增加 `worker_instance_id`、`heartbeat_at`、`claimed_at` 等诊断字段。
2. 如同步 ORM 明确造成事件循环阻塞，再迁移 Repository 层到 `AsyncSession`。
3. 如需要多机分布式执行，再单独评估整体迁移至 Procrastinate。

阶段 C 应独立设计、独立迁移、独立测试，不作为单进程并发上线前置条件。

### 灰度与回滚顺序

1. 记录现有两个 Worker 的任务吞吐、失败率和平均耗时。
2. 发布阶段 A 代码，但保持 `legacy_serial` 或并发数 1。
3. 完成一轮课程、热点采集、资料研究和图片任务回归。
4. 切换 `single_async`、并发数 2，观察至少一个完整工作日。
5. 出现上游压力时先把并发数降为 1；出现调度问题时切回 `legacy_serial`。
6. 如果单进程故障隔离不满足要求，再显式恢复旧多进程部署，不在同一启动脚本内保留含糊的双模式。

## 17. 测试与验收

### 17.1 单元测试

1. 并发上限为 2 时，两个假任务重叠执行，第三个任务等待。
2. 并发上限为 1 时，任务严格串行。
3. 一个任务抛出异常时，另一个任务正常完成。
4. 一个任务被取消时，另一个任务不受影响。
5. 每个任务使用不同 Session；调度、进度、终态短事务互不共享。
6. 心跳任务随执行任务启动，并在成功、失败、取消后关闭。
7. 领取 Task 创建失败时，任务不会永久停留在 `running`。
8. AnyIO task 异常会由任务入口消费，不产生未处理异常或取消兄弟任务。
9. 停机后不再领取新任务，已有任务按宽限期处理。
10. 任务超时会安全失败或按重试预算重新排队。
11. 停机 drain 期间活跃任务心跳继续续租。
12. `TaskGroup` 内一个任务失败不会取消其他任务。
13. 连续领取时不超过 `CapacityLimiter` 上限，不因子任务尚未调度而超领。

### 17.2 数据库集成测试

1. 两个并发协程不会领取同一个任务。
2. PostgreSQL `SKIP LOCKED` 和状态条件更新正常。
3. 心跳与进度更新并发时不覆盖彼此字段。
4. API 取消与 Worker 完成之间不存在旧状态覆盖。
5. Worker 中断后，任务能被下一次启动恢复。
6. 达到最大重试次数后任务正确失败。
7. `succeed()`、`fail()` 和取消终态在状态不匹配时返回未更新，旧协程不能覆盖新状态。
8. 当前进程注册表中的任务即使租约短暂过期，也不会被 `recover_expired()` 重新排队。
9. 内联图片子任务先从 `pending` 条件转换为 `running`，再完成受保护终态。
10. 模型或 HTTP 等待期间没有未提交的任务控制事务；阶段 B 进一步覆盖全部工作流事务。

### 17.3 真实业务验收

| 场景 | 预期 |
|---|---|
| 同时启动课程生成和热点采集 | 两个任务均进入 `running`，事件分别持续更新 |
| 同时生成两篇热点文章 | 进度和文章版本互不串写 |
| 图片生成和文本生成同时执行 | 阶段 A 受全局并发控制；阶段 B 的图片调用点限流不误阻塞文本调用 |
| 一个来源采集失败 | 采集任务按现有部分成功/失败规则收口，其他任务继续 |
| 课程任务中途重启 Worker | 租约过期后按现有重试与图片复用逻辑恢复 |
| 浏览器断开 SSE 后重连 | 通过 `Last-Event-ID` 补发缺失事件 |
| Worker 正在运行时重启 API | 已执行任务不受影响，API 恢复后可查询最新状态 |

### 17.4 性能验收标准

- 两个 I/O 型任务的墙钟时间应接近较慢任务的执行时间，而不是两者相加。
- 阶段 A 每 5 秒记录事件循环延迟；持续超过 500ms 时阻断并发放量并定位同步阻塞。阶段 B 再以 P95 小于 200ms 作为优化目标。
- 任务重复执行率为 0，除非明确发生租约过期恢复。
- PostgreSQL 连接池无持续耗尽、长事务和异常锁等待。
- 现有后端测试、Ruff、mypy、前端构建全部通过。

## 18. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 一个进程崩溃影响多个任务 | 多个任务同时中断 | 租约恢复、自动重启、任务幂等、并发数 1 回退 |
| 同步 ORM 阻塞事件循环 | SSE 和其他任务短暂延迟 | 短事务、阻塞监控、必要时 `to_thread`，后续 AsyncSession |
| Session 被协程共享 | 数据串写或事务污染 | 每任务独立 Session，代码审查和测试强制验证 |
| 图片/模型供应商限流 | 任务失败率上升 | 阶段 B 调用点限流、已有重试策略、供应商级限流 |
| 父任务等待子任务 | 并发槽位死锁 | 当前图片子任务保持内联；未来拆分需依赖调度 |
| 停机期间直接取消任务 | 状态停在 running 或结果丢失 | 宽限期、租约恢复、终态提交 shield |
| API 与旧 Worker 同时运行 | 任务重复领取 | 保留数据库原子领取和 `SKIP LOCKED`，切换时核对进程 |
| 并发导致同一实体重复写入 | 内容版本冲突 | 保留现有实体级活跃任务阻断和幂等检查 |

## 19. 回滚方案

回滚必须只依赖配置和启动方式，不依赖破坏性数据库操作：

1. 停止单进程异步 Worker。
2. 等待或恢复其过期租约。
3. 设置 `CHENGWENFANG_WORKER_EXECUTION_MODE=legacy_serial`。
4. 启动一个旧串行 Worker，必要时恢复第二个旧 Worker。
5. 检查 `jobs` 中 `running`、`pending` 和 `failed` 数量。
6. 通过任务详情和 SSE 验证已完成任务的事件和结果没有变化。

如果仅是并发引发上游压力，优先把 `CHENGWENFANG_WORKER_CONCURRENCY` 调为 1，而不是回滚整个版本。

## 20. 推荐落地结论

推荐采用以下最终配置：

```text
Worker 进程数：1
顶层任务并发数：2
文本模型并发数：2
图片模型并发数：1
来源采集并发数：2
数据库：继续使用现有 PostgreSQL 同步 SQLAlchemy Session
任务状态：继续使用 jobs + job_events + workflow_runs
前端：不改现有任务 API、SSE 和工作流节点展示
```

这套方案能够在不改变现有课程体系、热点雷达、资料池、文章生成和图片工作流的前提下，让一个 Worker 进程同时处理两个任务。它的边界也很明确：协程适合提高 I/O 等待期间的利用率，但不能提供进程级故障隔离；如果未来需要更高可靠性或更大吞吐，应考虑外部任务队列或恢复多进程，而不是无限增加单进程协程数量。
