# 课程生成消息提醒功能设计方案

> 文档版本：V1.0  
> 设计日期：2026-08-13  
> 当前阶段：方案已确认，暂不开发

## 0. 已确认决策

- 失败通知提供“重新执行”按钮，复用现有失败步骤重试能力。
- V1 仅制作成文坊站内通知，不申请浏览器或 Windows/macOS 系统通知权限。
- 通知中心只展示最近 30 天的消息。
- 超过 30 天的通知不再进入列表和未读数量统计；建议由每日或项目启动时的轻量清理逻辑物理删除，避免数据库长期积累无用数据。

## 1. 背景与目标

课程生成通常需要较长时间。用户离开执行轨迹页面后，目前只能主动返回页面查看任务是否完成，容易错过成功结果，也可能在任务失败后很久才发现问题。

本功能提供一个全局站内通知中心。当课程正式生成任务进入成功或失败终态时，系统生成一条持久化消息，并通过右上角铃铛、未读数字和轻量即时提示告知用户。

本期目标：

- 用户在成文坊任意页面都能看到未读通知数量。
- 课程生成成功或失败后只产生一条终态通知，不重复提醒。
- 用户可以从通知直接进入对应课程或执行记录。
- 刷新页面或重启项目后，消息和已读状态仍然保留。
- 通知功能不能影响课程生成任务本身；通知写入失败时，任务终态仍应正确提交。

## 2. V1 功能范围

### 2.1 纳入提醒

- 正式课程生成成功。
- 正式课程生成失败，包括首次失败和人工点击“重新执行失败步骤”后的再次失败。
- 重试最终成功时生成新的成功通知。

### 2.2 暂不纳入

- 单张图片生成、文章修复、mdnice 导出等独立任务。
- 任务排队、开始执行和中间进度通知。
- 浏览器系统通知，以及短信、邮件、微信、企业微信等外部渠道。
- 多用户权限和跨账号同步。

后续可复用同一通知模型扩展这些场景，不需要重新设计通知中心。

## 3. 入口与整体交互

### 3.1 顶部入口

在成文坊顶部栏右侧增加铃铛图标按钮。搜索框存在时，布局顺序为：

`搜索框 → 消息铃铛`

其他页面没有搜索框时，铃铛仍固定在顶部栏右侧，不随页面内容改变位置。

铃铛采用 Lucide `Bell` 图标，与现有图标体系一致。按钮使用现有图标按钮的尺寸、边框、悬停和聚焦样式，不设计成带文字的圆角按钮。

### 3.2 未读数字

- 有未读消息时，在铃铛右上角显示红色数字角标。
- 数量为 1～99 时显示实际数字；超过 99 显示 `99+`。
- 没有未读消息时不显示红点或数字。
- 未读数来自数据库，不使用 `localStorage` 作为事实来源。
- 打开通知面板本身不自动清空全部未读，避免用户尚未查看就丢失提醒语义。

### 3.3 通知面板

桌面端点击铃铛后，从顶部右侧打开宽约 380px 的浮层面板；窄屏端使用从右侧进入的全高抽屉。

面板不是独立页面，用户关闭后仍停留在原工作位置。

面板结构：

1. 标题“消息通知”与未读数量。
2. 筛选标签：“全部”“未读”。
3. “全部标为已读”操作，仅存在未读消息时可用。
4. 按时间倒序排列的消息列表。
5. 空状态：“暂无消息”或“没有未读消息”。
6. 首次加载骨架状态、加载失败状态与重试按钮。

### 3.4 消息项

每条消息包含：

- 状态图标：成功为绿色勾选，失败为红色警告。
- 标题。
- 一行结果摘要。
- 课程系列、课次和完成时间。
- 未读状态标记。
- 可执行操作。

成功示例：

```text
课程生成完成
第 5 课《在本地搭建 Python 编程环境》已生成，可查看课程内容。
模型原理 · 2 分钟前
[查看课程]
```

失败示例：

```text
课程生成失败
第 5 课《在本地搭建 Python 编程环境》生成失败：核心原理章节超过篇幅上限。
模型原理 · 2 分钟前
[查看原因]  [重新执行]
```

失败摘要优先显示经过整理的用户可读错误；错误过长时列表中最多显示两行，完整信息在执行轨迹中查看。

### 3.5 阅读规则

- 点击消息正文或其主要操作时，将该消息标记为已读。
- 单条消息提供“标为已读/未读”，放在更多菜单中，避免列表按钮过多。
- 点击“全部标为已读”只改变当前用户的阅读状态，不删除消息。
- 消息已读后继续保留在“全部”列表。

### 3.6 跳转规则

- 成功通知的主操作进入对应课程详情，并默认显示最新生成内容。
- 失败通知的主操作进入 `/executions?job={jobId}&course={courseId}`，定位到对应失败任务。
- 失败通知的“重新执行”复用现有失败步骤重试接口；点击前仍沿用现有确认交互。
- 目标课程或任务已不存在时，消息仍可查看，但操作显示为不可用，并提示“对应记录已不存在”。

## 4. 即时提醒方式

任务在用户当前打开成文坊期间进入终态时，除铃铛角标变化外，在右上角显示一条轻量 Toast：

- 成功：显示 4 秒，可点击“查看课程”。
- 失败：默认保留 8 秒，可点击“查看原因”；用户正在输入或操作弹窗时不抢焦点。
- 同一任务同一终态只弹出一次。
- 页面刷新后不补弹历史 Toast，但历史消息仍在通知列表中。

V1 推荐复用现有任务 SSE：当前页面正在监听课程生成任务时，收到终态后刷新未读数量并显示 Toast。为了覆盖用户已离开执行页面的情况，前端同时每 30 秒轻量轮询未读摘要；浏览器标签页重新获得焦点时立即刷新一次。

后续若任务量增加，可升级为全局通知 SSE，不影响数据库模型和界面结构。本期不调用浏览器 Notification API，也不弹出系统级授权请求。

## 5. 数据设计

新增 `notifications` 表，通知内容使用终态快照，避免课程后续改名导致历史消息失真。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | UUID/String | 通知 ID |
| `type` | String | `course_generation_succeeded` / `course_generation_failed` |
| `level` | String | `success` / `error` |
| `title` | String | 通知标题 |
| `message` | Text | 用户可读摘要 |
| `course_id` | String, nullable | 关联课程 |
| `job_id` | String, nullable | 关联后台任务 |
| `workflow_run_id` | String, nullable | 关联执行轨迹 |
| `series_name` | String | 生成当时的系列名称快照 |
| `course_title` | String | 生成当时的课程标题快照 |
| `lesson_no` | Integer | 生成当时的课次快照 |
| `status` | String | `unread` / `read` |
| `read_at` | DateTime, nullable | 阅读时间 |
| `dedupe_key` | String, unique | 防止同一终态重复写入 |
| `metadata_json` | JSON | 错误码、重试来源等扩展信息 |
| `created_at` | DateTime | 终态通知创建时间 |

当前应用是单用户本地成文坊，V1 可直接将已读状态放在通知表中。若未来支持多用户，再拆分为 `notifications` 与 `notification_receipts`，本期无需提前增加复杂度。

### 5.1 去重规则

建议使用：

```text
dedupe_key = job_id + ":" + terminal_status
```

同一任务重复调用成功/失败提交逻辑时，不会产生重复消息。人工重试会创建新的任务或新的执行终态，因此会产生一条新的结果通知，完整保留每次尝试历史。

## 6. 后端触发设计

通知应在通用 `JobService.succeed()` 和 `JobService.fail()` 完成任务终态持久化时创建，但仅当以下条件同时成立：

- `job.type` 是课程完整生成任务。
- 任务从非终态首次进入 `succeeded` 或 `failed`。

流程：

1. worker 完成课程任务。
2. 提交 Job 成功或失败终态。
3. 在同一数据库事务内尝试写入通知。
4. 通过唯一 `dedupe_key` 保证幂等。
5. 写入任务终态事件，供现有 SSE 使用。

通知内容组装建议由独立 `NotificationService` 负责，`JobService` 只传入任务、课程和错误信息，避免任务服务承担展示文案逻辑。

如果通知创建发生非预期错误，应记录日志但不能反向把已完成的课程生成任务改成失败。实现时可以将通知写入作为独立容错步骤，或通过捕获唯一约束之外的异常实现降级。

## 7. API 设计

### 7.1 获取通知列表

```http
GET /api/notifications?status=all|unread&limit=30&cursor={cursor}
```

返回通知列表、下一页游标和当前未读数。

### 7.2 获取未读摘要

```http
GET /api/notifications/summary
```

```json
{
  "unreadCount": 3,
  "latestCreatedAt": "2026-08-13T15:30:00+08:00"
}
```

用于顶部铃铛轻量轮询，不返回完整列表。

### 7.3 单条标记已读

```http
PATCH /api/notifications/{notificationId}
{
  "read": true
}
```

### 7.4 全部标记已读

```http
POST /api/notifications/read-all
```

接口返回新的未读数量，前端不自行猜测。

## 8. 状态与边界处理

### 8.1 失败后重试

- 原失败通知不会被成功通知覆盖或改写。
- 用户重试后成功，新增成功通知。
- 新成功通知可在 `metadata_json` 中记录 `retryOfJobId`，未来可展示“重试后完成”。

### 8.2 任务取消

V1 默认不生成取消通知。取消是用户主动行为，通常不需要提醒；后续如有自动取消或超时取消，可以扩展为警告通知。

### 8.3 项目重启

- 已落库通知不丢失。
- worker 启动时恢复的任务最终完成后，照常创建通知。
- 不根据历史 Job 批量补建旧通知，避免首次上线突然出现大量历史消息。

### 8.4 消息保留

V1 不提供逐条删除，减少误删和恢复逻辑。通知列表、未读摘要和“全部标为已读”只处理最近 30 天的数据。

超过 30 天的消息不再展示，也不计入铃铛未读数字。建议使用轻量清理机制物理删除过期通知：每日首次访问通知接口时最多执行一次，或在项目启动后异步执行一次。清理失败只记录日志，不影响通知查询和课程任务。

## 9. 视觉与响应式规范

- 铃铛按钮稳定为 40×40px，不因角标出现而改变顶部布局。
- 角标最小 18×18px，红底白字，数字不挤压铃铛图标。
- 面板圆角不超过现有 8px 组件规范。
- 消息项使用分隔线列表，不使用层层嵌套卡片。
- 未读项使用轻微背景差异和左侧状态点，不整块使用高饱和红/绿背景。
- 成功色只用于图标和状态文字；失败色只用于错误图标、错误摘要和主要错误操作。
- 键盘支持：铃铛可聚焦，`Enter/Space` 打开，`Esc` 关闭，打开后焦点进入面板标题或首个可操作项。
- 移动端抽屉宽度为视口宽度，上限 420px；消息标题、课程名和错误文案允许换行，不能横向溢出。

## 10. 可观测性与验收

### 10.1 日志

记录以下事件，但不保存正文或密钥：

- `notification_created`
- `notification_deduplicated`
- `notification_marked_read`
- `notification_read_all`
- `notification_creation_failed`

### 10.2 核心验收场景

1. 正式课程生成成功后产生一条未读成功消息，未读数加一。
2. 正式课程生成失败后产生一条未读失败消息，包含可读原因。
3. 同一任务重复提交终态不产生重复消息。
4. 点击失败消息进入对应执行记录，并定位正确 Job。
5. 点击成功消息进入对应课程详情。
6. 标记单条已读后角标数量正确减少。
7. 全部标为已读后角标消失，历史消息仍存在。
8. 刷新页面、重启前后端后消息与已读状态不丢失。
9. 通知写入异常不改变课程任务已经成功或失败的终态。
10. 桌面端和 390px 窄屏无横向溢出，面板不会遮挡后无法关闭。
11. 同时完成多个任务时，通知按终态时间倒序，未读数准确。

## 11. 推荐实施顺序

1. 数据表、迁移和 `NotificationService`。
2. 课程任务成功/失败终态触发与去重测试。
3. 通知列表、摘要、已读 API。
4. 顶部铃铛、未读角标和通知面板。
5. 任务 SSE 联动、轮询和 Toast。
6. 桌面端、窄屏、刷新重启与并发任务验收。

## 12. 产品决策结论

1. 失败通知同时提供“查看原因”和“重新执行”操作。
2. V1 仅使用成文坊内铃铛、未读角标和 Toast，不制作浏览器或操作系统级通知。
3. 通知中心展示最近 30 天消息，过期消息不计入未读数量，并由轻量清理机制删除。

当前方案已具备进入开发阶段所需的产品决策，无剩余阻塞项。
