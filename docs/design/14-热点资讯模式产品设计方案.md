# 热点资讯模式产品设计方案

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 文档状态 | 已确认方案，待开发 |
| 设计日期 | 2026-08-18 |
| 适用项目 | 内容成文坊 |
| 新增模式 | 热点资讯模式 |
| 首个主题 | AI 热点前沿 |
| 首发平台 | 微信公众号 |
| 采集方式 | 用户手动触发 |

本文档定义热点资讯模式的产品边界、页面结构、核心流程和人工决策点，不包含代码实现。

## 2. 已确认决策

1. 内容读者包含开发者、创业者和 AI 行业从业者。
2. 允许接入多个平台、网站和 GitHub 等来源。
3. 第一阶段由用户手动点击触发采集，不做定时自动采集。
4. 候选选题必须由用户手动确认后才能进入写作流程。
5. 重点生成有一定深度的分析内容，不追求当天快讯速度。
6. 文章允许加入作者观点，但必须区分事实、来源观点和作者判断。
7. 第一阶段只生成微信公众号文章。
8. 接受配置 GitHub Token、搜索 API、平台 Cookie 等凭据。

## 3. 产品定位

热点资讯模式不是简单的新闻摘要器，而是一套“发现热点、判断价值、补充证据、形成观点、生成深度文章”的内容生产系统。

核心目标：

- 降低从多个来源发现 AI 资讯的时间成本。
- 将同一事件的多个来源聚合为一个可理解的热点事件。
- 区分“热门”与“值得深入写作”。
- 在文章生成前完成事实、时间、来源和争议信息整理。
- 保留作者观点，但避免将观点伪装成事实。
- 所有文章都能追溯到原始来源和生成过程。

明确不做：

- 第一阶段不自动发布公众号文章。
- 不因单一来源标题热度直接生成文章。
- 不把未经核实的社交平台内容当作事实。
- 不默认抓取需要绕过登录、验证码或访问限制的页面。
- 不在后台无限重试失败来源或长时间保持“执行中”。

## 4. 信息架构

左侧导航建议为：

```text

课程体系教学模式
  └─ 课程路线

热点资讯模式
  └─ 热点雷达

```

点击“热点资讯模式”进入模式总览，展示“AI 热点前沿”主题卡片。点击主题卡片进入热点雷达。

主题工作区包含五个视图：

1. 热点雷达：查看最近采集、热度上升和待核验事件。
2. 候选选题：查看系统推荐的可写选题。
3. 选题详情：查看事件时间线、来源、事实和写作角度。
4. 写作队列：查看已确认选题的简报、文章和审核状态。
5. 文章库：查看该主题生成的公众号文章及来源关联。

## 5. 热点雷达

### 5.1 顶部操作

- `开始采集`：创建一次手动采集任务。
- `查看采集记录`：查看最近任务及每个来源的成功、跳过和失败原因。
- `来源筛选`：按来源类型、可信等级和状态筛选。
- `时间范围`：最近 24 小时、3 天、7 天、自定义。
- `刷新`：只刷新已持久化数据，不隐式触发采集。

### 5.2 统计区

- 本次新增条目
- 聚合热点数
- 高价值候选数
- 待人工确认数
- 需要事实核验数
- 采集失败来源数

### 5.3 热点列表

每条热点展示：

- 热点标题
- 一句话事件摘要
- 热度分
- 写作价值分
- 可信度等级
- 来源数量
- 首次发现时间和最后更新时间
- 当前状态
- 推荐写作类型

状态建议：

```text
新发现 → 已聚合 → 待评估 → 候选选题 → 已确认 → 写作中
                                   ├→ 暂不处理
                                   ├→ 已忽略
                                   └→ 已过期
```

## 6. 选题判断

系统为每个热点生成两套分数：

### 6.1 热度分

- 多来源出现数量：25%
- 讨论量及增长速度：25%
- GitHub、搜索或社区增量：20%
- 来源影响力：15%
- 时间新鲜度：15%

### 6.2 写作价值分

- 与 AI 主题相关程度：20%
- 对开发者、创业者或从业者的实际影响：20%
- 可解释和可延展程度：20%
- 是否存在可靠一手资料：15%
- 与历史文章的差异：15%
- 是否符合账号定位：10%

### 6.3 结果分层

```text
高热度 + 高价值：优先推荐
低热度 + 高价值：深度储备
高热度 + 低价值：观察或生成简讯建议
低热度 + 低价值：自动归档
```

评分必须同时保存评分结果和简短理由，不能只保存一个不可解释的数字。

## 7. 选题详情

详情页按“先事实、后判断、再写作”的顺序组织：

1. 事件概览：发生了什么、何时发生、涉及谁。
2. 来源时间线：官方来源、论文、代码、媒体和社区信息。
3. 事实状态：已确认、待确认、存在争议、疑似错误。
4. 热度趋势：来源数量、讨论变化和时间趋势。
5. 影响分析：对开发者、创业者和行业从业者的可能影响。
6. 历史关联：与已生成文章和历史热点的关系。
7. 推荐角度：系统提出 2～4 个可写方向。
8. 写作设置：文章类型、字数范围、正文配图数量。

人工操作：

- 确认选题
- 修改标题或写作角度
- 补充作者观点
- 标记需要补证的事实
- 暂不处理
- 忽略并说明原因

## 8. 文章生产

确认选题后，先生成“选题分析简报”，简报确认后才能生成文章正文。

简报必须包含：

- 事件是什么
- 为什么受到关注
- 已确认事实
- 尚未确认信息
- 关键来源
- 对不同读者的影响
- 作者可以加入的判断
- 推荐文章结构
- 不宜使用的结论
- 需要在正文中标注的来源

文章类型建议：

| 类型 | 建议字数 | 适用场景 |
|---|---:|---|
| 热点解读 | 2000～4000 字 | 事件影响和背景分析 |
| 产品或模型分析 | 3000～5000 字 | 新产品、新模型、新功能 |
| 技术原理分析 | 4000～6000 字 | 论文、模型和开源实现 |
| 行业影响分析 | 3000～6000 字 | 创业、商业和产业变化 |
| 开源项目介绍 | 3000～6000 字 | GitHub 项目和实操价值 |
| 多方观点整理 | 2000～4000 字 | 存在争议或多种解读 |

作者观点必须使用明确表达区分：

- “目前可以确认的是……”：事实。
- “官方认为……”：来源观点。
- “从这个变化来看，我更倾向于认为……”：作者判断。
- “这里仍然不能确定……”：不确定性。

## 9. 人工确认点

第一阶段设置三个硬确认点：

1. **选题确认**：没有人工确认，不能生成文章。
2. **简报确认**：简报中的事实、角度和观点范围需要确认。
3. **成稿审核**：审核来源、数字、日期、引用、观点边界和公众号排版。

文章生成失败、来源失败或事实核验失败时，任务必须进入明确终态，不得一直显示“执行中”。

## 10. 通知

以下状态发送站内通知：

- 手动采集成功
- 采集部分成功
- 采集全部失败
- 发现高价值热点
- 简报生成成功或失败
- 文章生成成功或失败
- 事实核验发现阻断问题
- 文章进入待人工审核

通知点击后应直接进入对应采集任务、热点、简报或文章详情。

## 11. 第一阶段验收标准

- 可以手动触发一次多来源采集。
- 每个来源都有独立状态和失败原因。
- 相同事件能够合并为一个热点。
- 热点同时展示热度分、写作价值分和理由。
- 用户可以确认、忽略、暂缓和修改选题。
- 未确认的选题不能生成文章。
- 文章能够查看原始来源和事实核验结果。
- 文章生成成功或失败都有明确通知。
- 采集失败不会拖住整条任务。
