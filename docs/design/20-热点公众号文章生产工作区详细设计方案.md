# 热点公众号文章生产工作区详细设计方案

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 文档状态 | 方案已确认，待开发 |
| 设计日期 | 2026-08-20 |
| 适用模式 | 热点资讯模式 |
| 首发主题 | AI 热点前沿 |
| 目标平台 | 微信公众号 |
| 前置文档 | 14、15、16、18、19 号热点资讯设计文档 |

本文定义热点资讯模式从“已确认简报”到“可复制发布稿”的完整文章生产能力。重点解决当前公众号文章仅由固定模板生成、只能查看、不能编辑、缺少事实复检和无法进入原生排版的问题。

## 2. 背景与问题

### 2.1 当前链路

```text
采集 → 聚合评分 → 确认选题 → 生成并确认简报 → 固定模板文章 → 查看全文
```

当前已经具备：

- 独立热点、来源证据、单份当前简报。
- 独立热点文章和文章版本表。
- 后台文章生成任务、进度与运行记录。
- 文章来源快照和简报确认门槛。
- Markdown 全文查看和复制。

### 2.2 核心问题

1. 文章由确定性模板拼装，不是针对热点内容生成的完整成稿。
2. 不同热点共用大量固定段落，内容同质化严重。
3. 文章只能预览，无法修改、保存或局部重写。
4. 来源证据与文章陈述没有逐条对应关系。
5. 没有热点专属自动审核和人工审核状态。
6. 课程文章的编辑、审核、排版接口外键绑定 `articles`，不能直接接收 `hot_news_articles`。
7. 当前选题详情弹窗承载了过多生产职责，不适合继续扩展成编辑器。

## 3. 产品目标

建立热点模式自己的文章生产工作区：

```text
确认简报
  → AI 生成完整文章
  → 人工编辑与局部重写
  → 事实复检
  → 人工审核
  → 公众号排版
  → 复制富文本或保存发布快照
```

成功标准：

- 文章围绕当前热点和来源生成，不再出现跨热点复用的固定分析段落。
- 用户始终能看见事实依据、待核实项和当前保存状态。
- 所有 AI 修改都必须由用户显式采纳或生成新文章版本。
- 文章进入排版前完成事实边界检查。
- 热点文章继续与课程文章隔离，但复用通用 Markdown 渲染和公众号排版内核。

## 4. 非目标

- 首期不直接调用微信公众号发布 API。
- 首期不做多人实时协同编辑。
- 不把热点文章塞入课程、系列或课程序号模型。
- 不复用课程特有的上下节衔接、学习目标、课程摘要和课程配图规则。
- 不允许模型自行联网补充未进入来源快照的信息。
- 不自动采纳局部重写或审核修复结果。

## 5. 信息架构

### 5.1 入口调整

选题详情弹窗继续承担：

- 来源证据浏览。
- 当前简报确认。
- 文章状态摘要。
- `生成文章` 或 `进入文章工作区` 入口。

弹窗不再承担全文编辑、审核或排版。

文章工作区地址：

```text
/modes/hot-news/topics/{topicId}/articles/{articleId}
```

后续文章库地址：

```text
/modes/hot-news/articles
```

### 5.2 工作区页面结构

```text
┌ 顶部栏：返回、标题、版本、保存状态、主要操作 ┐
├ 左侧 280px ─────┬ 中间编辑区 ─────┬ 右侧预览区 ┤
│ 来源与事实边界   │ Markdown 编辑器  │ 公众号预览   │
│ 已确认事实       │ 标题与正文        │ 桌面/手机     │
│ 待核实信息       │ 问题行内标记      │ 排版主题       │
│ 来源快照         │                  │               │
├ 底部抽屉：事实复检结果 / 历史版本 / 生成记录 ┤
└──────────────────────────────────────────┘
```

桌面端优先保证高密度生产效率。宽度不足时，左侧事实栏和右侧预览改为可切换侧栏；移动端采用 `正文 / 来源 / 预览 / 审核` 四个标签页，不压缩成不可读三栏。

## 6. 页面与交互设计

### 6.1 顶部栏

展示：

- 热点标题和文章状态。
- 当前文章版本、字数、更新时间。
- `已保存`、`有未保存修改`、`保存中`、`保存失败`。
- `保存文章`。
- `AI 重写` 菜单。
- `执行事实复检`。
- `进入排版`。

状态变化时页面尺寸不得跳动。所有异步操作都有进度、成功和失败终态。

### 6.2 来源与事实边界

分为三个标签：

1. **已确认事实**：简报中的 `confirmedFacts`，显示支持来源数量。
2. **待核实**：简报中的 `unknowns`、冲突项和缺失信息。
3. **来源**：来源名称、类型、发布时间、可信等级、原始链接和快照时间。

点击事实或审核问题时，中间编辑器滚动并高亮相关段落。点击正文中的来源标记时，左侧定位到对应来源。

### 6.3 Markdown 编辑器

首期支持：

- 标题和正文编辑。
- Markdown 语法高亮或普通等宽文本编辑。
- 撤销、重做、查找。
- 字数统计。
- 显式保存。
- 离开页面未保存确认。
- 错误段落标记。
- 选中文本后局部重写。

不在用户每次输入时创建数据库版本。浏览器内可维护临时草稿，正式版本由显式保存产生。

### 6.4 AI 操作

全文操作：

- 重新生成全文。
- 更换文章结构。
- 更换语气。
- 压缩或扩展到目标字数。
- 生成 3～5 个标题候选。
- 重写开头或结尾。

局部操作：

- 更清楚。
- 更简洁。
- 增加分析深度。
- 降低绝对化表达。
- 补充来源标记。
- 自定义要求。

所有 AI 操作输出差异预览，提供 `采纳`、`放弃`、`重新生成`。未采纳内容不写入正文。

### 6.5 公众号预览

复用现有 `publishing/render` 渲染内核和主题系统：

- Markdown 与预览使用同一份浏览器草稿。
- 支持桌面和 375px 手机预览。
- 支持选择启用中的排版主题。
- 展示阻断与警告诊断。
- 通过审核后允许复制公众号富文本。

不复用课程文章的 `article_layouts` 和 `publishing_snapshots` 外键结构，热点模式新增对应实体。

## 7. AI 文章生成设计

### 7.1 输入包

生成节点只接收受控结构化输入：

```json
{
  "topic": {"title": "", "summary": "", "scoreReason": "", "lifecycle": ""},
  "brief": {
    "articleType": "",
    "targetAudience": "",
    "angle": "",
    "confirmedFacts": [],
    "unknowns": [],
    "mustNotClaim": [],
    "authorJudgementBoundary": ""
  },
  "sources": [{"id": "", "title": "", "content": "", "url": "", "trust": ""}],
  "preferences": {"targetWords": 3000, "tone": "克制、清晰、有判断"},
  "authorStyle": null
}
```

来源正文需要有长度上限和总 token 预算；超长来源先做可追溯摘要，但关键数字、日期和引用保留原句。

### 7.2 Prompt 规则

- 只能使用输入包中的事实。
- 不得将 `unknowns` 写成确定事实。
- 作者分析必须使用可识别的判断表达。
- 数字、日期、版本号、机构名称必须能映射到来源。
- 不加入课程编号、学习目标、上下节衔接或课程小结。
- 正文不展示生产提示词和内部审核标签。
- 输出完整 Markdown，不输出 JSON 包裹或解释文字。

### 7.3 推荐生成流程

```text
加载已确认简报与来源快照
→ 生成文章提纲
→ 校验提纲覆盖事实与读者价值
→ 分章节生成
→ 合并与去重复
→ 事实边界预检
→ 保存候选版本
```

首期可以一次生成完整文章，但接口和工作流节点应按上述阶段建模，便于以后支持断点续跑和章节级重试。

### 7.4 模型失败处理

- 超时：任务失败，可重试，不覆盖现有文章。
- 内容过短或缺区块：阻断保存候选结果。
- 引入无来源数字：标记审核失败，不自动发布。
- 简报在生成期间变化：拒绝提交，提示重新生成。
- 用户在生成期间编辑文章：候选结果独立保存，不覆盖编辑内容。

## 8. 事实复检设计

### 8.1 检查层级

第一层为确定性规则：

- URL 和 Markdown 链接有效性。
- 数字、日期、百分比、货币、版本号扫描。
- 禁止绝对化表达。
- 简报 `mustNotClaim` 文本相似度匹配。
- 来源快照 Hash 是否变化。
- 当前正文是否对应最新保存版本。

第二层为 AI 语义核验：

- 提取正文中的可验证陈述。
- 将陈述映射到一个或多个来源。
- 判断支持、部分支持、冲突、无依据。
- 区分事实、来源观点和作者判断。

### 8.2 审核结果结构

每个问题包含：

```text
问题代码、严重级别、正文位置、原文片段、说明、来源、建议修复、是否阻断
```

严重级别：

- `error`：无来源关键事实、事实冲突、篡改数字，阻断排版。
- `warning`：来源单一、措辞过强、信息可能过期，可人工确认后继续。
- `info`：风格或可读性建议。

### 8.3 人工审核

人工审核绑定精确文章版本：

- `pending`：未审核。
- `approved`：通过。
- `rejected`：退回修改。

文章产生新版本后，旧审核保留但当前状态恢复为 `pending`。审核通过时记录备注、时间和当时的审核报告 ID。

## 9. 数据模型

### 9.1 保留模型

- `hot_news_articles`：当前文章和当前版本指针。
- `hot_news_article_versions`：不可变文章版本。
- `topic_briefs`：当前简报记录，界面不暴露版本概念。

### 9.2 调整字段

`hot_news_articles` 建议增加：

| 字段 | 类型 | 用途 |
|---|---|---|
| `review_status` | varchar | pending / passed / failed |
| `human_review_status` | varchar | pending / approved / rejected |
| `latest_audit_id` | nullable FK | 当前事实复检 |
| `generation_mode` | varchar | template / ai |
| `updated_by` | varchar | ai / user / repair |

`hot_news_article_versions` 建议增加：

| 字段 | 类型 | 用途 |
|---|---|---|
| `brief_snapshot_json` | JSON | 保存时使用的简报快照 |
| `source_snapshot_json` | JSON | 保存时使用的来源快照 |
| `change_summary` | text | 用户输入或 AI 操作说明 |
| `created_by` | varchar | ai / user / repair |

### 9.3 新增模型

1. `hot_news_article_audits`
   - 绑定文章版本。
   - 保存规则结果、AI 结果、总状态和运行 ID。

2. `hot_news_article_audit_issues`
   - 保存正文位置、来源映射、严重级别和修复建议。

3. `hot_news_human_reviews`
   - 绑定热点文章版本，保存通过或退回决定。

4. `hot_news_article_layouts`
   - 热点文章当前排版主题和显式保存配置。

5. `hot_news_publishing_snapshots`
   - 绑定热点文章版本、主题版本、HTML、图片清单和诊断。

6. `hot_news_rewrite_candidates`
   - 保存待采纳的全文或局部 AI 改写结果、原文 Hash 和指令。

### 9.4 为什么不做统一多态文章表

当前课程文章被 `course_id`、课程版本对、课程审核和图片工作流深度绑定。立即将其改为多态内容实体会扩大迁移风险。首期采用热点独立表，并抽取无状态通用服务：Markdown 渲染、主题选择、富文本复制、差异计算。待两套流程稳定后再评估统一 `content_documents` 抽象。

## 10. API 设计

### 10.1 文章读取与保存

```text
GET  /api/hot-news/articles/{id}
PUT  /api/hot-news/articles/{id}
GET  /api/hot-news/articles/{id}/versions
GET  /api/hot-news/articles/{id}/versions/{versionNo}
POST /api/hot-news/articles/{id}/versions/{versionNo}/restore
```

保存请求包含 `baseContentHash`，服务端执行乐观锁检查；正文已变化时返回 `409 HOT_NEWS_ARTICLE_STALE`。

### 10.2 AI 生成与改写

```text
POST /api/hot-news/briefs/{id}/generate-article
POST /api/hot-news/articles/{id}/rewrite
GET  /api/hot-news/articles/{id}/rewrite-candidates
POST /api/hot-news/rewrite-candidates/{id}/accept
DELETE /api/hot-news/rewrite-candidates/{id}
```

局部重写请求必须包含选区起止位置、选区原文 Hash 和用户指令。采纳时正文 Hash 不一致则拒绝应用。

### 10.3 审核

```text
POST /api/hot-news/articles/{id}/audits
GET  /api/hot-news/articles/{id}/audits/current
PUT  /api/hot-news/articles/{id}/human-review
GET  /api/hot-news/articles/{id}/human-review
```

### 10.4 排版

通用渲染继续使用：

```text
POST /api/publishing/render
GET  /api/publishing/themes
```

热点持久化使用独立接口：

```text
GET  /api/hot-news/articles/{id}/layout
PUT  /api/hot-news/articles/{id}/layout
POST /api/hot-news/articles/{id}/publishing-snapshots
GET  /api/hot-news/articles/{id}/publishing-snapshots
```

## 11. 状态机

```text
简报待确认
  → 简报已确认
  → 生成中
  → 草稿待编辑
  → 待事实复检
  → 复检失败 ─→ 修改后重新复检
  → 待人工审核
  → 审核退回 ─→ 修改后重新复检
  → 审核通过
  → 已排版
  → 已生成发布快照
```

建议文章主状态：

```text
generating / draft / auditing / needs_revision / ready / published_snapshot
```

审核状态和排版状态使用独立字段，不把所有组合压缩成一个不可维护的状态枚举。

## 12. 来源更新与文章失效

- 简报来源无变化：不修改简报，不影响文章。
- 简报来源新增：覆盖当前简报并重置简报确认。
- 已有文章不自动覆盖，标记 `source_update_available`。
- 用户确认新简报后，可选择“基于新简报生成候选文章”或保持当前文章。
- 已保存文章版本永久保留当时的简报和来源快照。
- 来源网页后来发生变化，不重写历史快照。

## 13. 权限、安全与成本

- 来源正文、用户指令和模型输出都视为不可信输入。
- Prompt 明确忽略来源正文中的操作指令。
- Markdown 渲染继续使用现有标签、属性、协议白名单。
- AI 请求记录模型、Prompt 版本、token 用量、延迟和错误，但不记录凭据。
- 全文重写显示预计成本或至少显示将调用 AI。
- 连续点击使用任务幂等键防止重复计费。
- 未采纳候选结果可以设置保留期，定期归档而非无限增长。

## 14. 可观测性

每次生成或审核记录：

- 文章、简报和来源快照 ID/Hash。
- 工作流运行 ID 和节点产物。
- Prompt 版本与模型。
- 输入输出 token、耗时、重试次数。
- 失败代码和用户可理解错误。
- 用户是否采纳候选结果。

关键指标：生成成功率、平均耗时、事实问题数、重写采纳率、从选题确认到发布快照的时间。

## 15. 迁移与兼容

1. 现有 `template` 文章保留，标记 `generation_mode=template`。
2. 首次打开工作区时可继续编辑旧文章，也可点击“使用 AI 重新生成”。
3. 不删除现有文章版本和来源快照。
4. 选题详情仍显示文章摘要，但主操作改为“进入文章工作区”。
5. 课程文章和现有排版接口保持不变。

## 16. 分阶段实施

### 阶段 A：独立文章工作区

- 新路由和页面骨架。
- 热点文章显式保存与版本历史。
- Markdown 编辑、未保存保护、普通预览。
- 选题详情改为工作区入口。

验收：编辑保存产生一个新版本；刷新后内容一致；并发旧 Hash 保存返回 409。

### 阶段 B：AI 完整生成

- 热点专属 Prompt 和生成节点。
- 结构化输入包和来源 token 预算。
- 候选结果与差异预览。
- 替换确定性模板为 AI 主路径，模板仅作上游不可用时的显式降级方案。

验收：不同热点不存在固定通用正文；所有数字和事实来自输入来源；失败不覆盖现有文章。

### 阶段 C：事实复检与人工审核

- 确定性规则和 AI 陈述映射。
- 审核问题列表和正文定位。
- 人工通过/退回。
- 新文章版本自动使当前审核失效。

验收：无来源关键数字能阻断；警告可追溯到正文和来源；审核严格绑定版本。

### 阶段 D：公众号排版与发布快照

- 复用渲染内核和主题系统。
- 热点独立布局与快照表。
- 手机预览、富文本复制、发布诊断。

验收：预览、复制和快照使用同一 HTML；微信编辑器真实粘贴保持样式；快照可追溯。

### 阶段 E：效率能力

- 局部重写、标题候选、开头和结尾重写。
- 来源更新提醒。
- 封面和正文图片工作流。
- 文章库和筛选。

## 17. 测试策略

后端：

- 简报确认门槛、来源快照锁定。
- AI 失败不覆盖、重复请求幂等。
- 显式保存、乐观锁、版本恢复。
- 审核绑定版本和失效规则。
- 来源更新后的简报与文章状态。
- 热点排版快照外键和 Hash。

前端：

- 未保存离开保护。
- 编辑器、预览和字数同步。
- AI 候选采纳/放弃。
- 审核问题定位。
- 桌面三栏和移动标签布局。
- 长标题、长来源、长正文无重叠或横向溢出。

端到端：

```text
确认简报 → AI 生成 → 编辑保存 → 事实复检 → 人工通过 → 排版 → 复制富文本
```

## 18. 已确认产品决策

### 决策 1：文章保存方式

已确认：**显式保存**。编辑过程只在浏览器保留，点击“保存文章”才创建版本，并在离开页面时提示未保存修改。

备选：自动保存草稿，但正式版本仍需显式提交。实现和恢复逻辑更复杂。

### 决策 2：AI 重新生成方式

已确认：**先生成候选稿，用户查看差异后采纳**。绝不直接覆盖当前文章。

备选：直接生成新版本。操作更快，但容易丢失人工编辑上下文。

### 决策 3：事实复检门槛

已确认：**阻断问题必须解决或明确人工豁免，才能进入排版；警告不阻断**。人工豁免需要填写原因并进入审计记录。

备选：复检只提示不阻断。自由度高，但事实风险明显更大。

## 19. 推荐结论

采用“热点独立业务模型 + 通用无状态能力复用”的方案：

- 热点独立维护文章、审核、布局和发布快照。
- 复用 Markdown 渲染器、公众号主题、富文本复制、任务系统和工作流节点记录。
- 不进行课程文章多态化重构。
- 先完成可编辑、可保存、可预览的文章工作区，再替换 AI 生成，随后补事实复检和排版闭环。

该顺序能最早交付可用价值，同时避免将 AI、审核、排版和底层模型重构一次性耦合。

## 20. 事实判断与文章表达边界补充

### 20.1 判断前置

事实可信度、来源评分、冲突识别和 AI 资料判断只发生在素材池与资料获取阶段。文章生成开始前，系统只向生成节点提供已经确定可用的事实结论、来源引用和写作素材。

### 20.2 成品不展示内部判断

公众号文章不得出现以下内部工作语言：

- 可信度评分、证据分数、来源等级；
- 已核验、待核验、冲突证据、独立来源不足；
- 推荐写作角度、不宜直接声称、建议继续补充资料；
- AI 判断过程、素材池状态和审核流程说明。

文章只呈现确定后的事实、解释、影响分析和结论。来源快照可以作为文章末尾的引用附录，但不展示评分和内部状态。

### 20.3 后台仍保留硬性校验

事实复检继续在后台执行，用于阻止正文编造来源之外的数字、时间、人物和性能结论；校验结果写入审核记录，不直接改写成文章中的“可信度说明”。
